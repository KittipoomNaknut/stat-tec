## การทดลอง

### รอบที่ 1 — สมมติฐาน: จุดอ้างอิง (กลางไหล่ + สเกล) ไหล ✗

cursor = (ข้อมือ − กลางไหล่) ÷ สเกล ถ้าจุดอ้างอิงขยับตามแขน (ไหล่ยกตามแขน หรือสเกลสลับไปมาระหว่างความกว้างไหล่กับ 0.65 × ลำตัว) cursor จะไหลเองได้ จึงลองกรองจุดอ้างอิงให้ช้า

| จุดอ้างอิง (side zone) | steady\* | กดติด | หลุด | lag |
| ---------------------- | -------- | ----- | ---- | --- |
| ทุกเฟรม (เดิม)         | 60.0     | 23    | 6    | 36  |
| กรอง τ 250 ms          | 59.1     | 23    | 8    | 41  |
| กรอง τ 1000 ms         | 64.1     | 20    | 9    | 82  |
| กรอง τ 2000 ms         | 69.3     | 19    | 12   | 154 |

\*ตอนนั้นยังใช้ hold spread ทั้งช่วงที่ค้าง (ตัววัด steady มาเพิ่มในรอบที่ 2)

**ยิ่งแย่ลง:** เวลาคนโยกตัว ข้อมือก็โยกไปด้วย จุดอ้างอิงที่ขยับตามทุกเฟรมจึงหักการโยกตัวออกให้อยู่แล้ว → ทิ้งแนวทางนี้

### รอบที่ 2 — หลุดเป้าจริงหรือแค่ลากผ่าน

ดูทุกครั้งที่หลุดเป้า (ค้าง 30–80% แล้วหลุด):

- ทุกครั้ง cursor พุ่งออกเร็ว 1,000–4,300 px/s ข้อมือในภาพกล้องไม่ได้กระโดด (2–13 px) จึงไม่ใช่ tracking พัง
- session ล่าสุดมีแค่ **2 ใน 6** ครั้งที่ผู้เล่นกลับมากดปุ่มเดิม ที่เหลือ ปุ่มถัดไปที่กดติดคือปุ่มข้าง ๆ หลังจากนั้น 1.2 s พอดี แปลว่า**ลากผ่านปุ่มระหว่างทาง** ไม่ใช่ความล้มเหลว

ตัววัด "หลุดเป้า" จึงปนสองเรื่องเข้าด้วยกัน → เพิ่มตัววัด **steady** ที่วัดเฉพาะช่วงที่ตั้งใจถือนิ่ง ค่าฐาน: **13.6 / 22.0 px**

| mc / β / deadband     | shake | steady | lag |
| --------------------- | ----- | ------ | --- |
| 0.8 / 8 / 0.4% (เดิม) | 1.84  | 13.6   | 36  |
| 0.3 / 8 / 0.4%        | 1.65  | 13.6   | 38  |

| 0.8 / 8 / 0.8%        | 1.91  | 12.6   | 43  |
| 0.3 / 20 / 0.8%       | 2.54  | 12.4   | 30  |

steady แทบไม่ขยับ (ดีสุด −9%) แปลว่าที่เหลือคือ**การไหลความถี่ต่ำ** (แขนโยกจริง + โมเดลคลาดช้า ๆ) ตัวกรองความถี่ลบไม่ได้ ถ้าไม่ทำให้ cursor หน่วงไปด้วย

### รอบที่ 4 — PRISM: อัตราขยายตามความเร็วมือ ✓

แนวคิดจาก PRISM (Frees, Kessler & Kay 2007, _ACM TOCHI_):

- มือช้า: cursor ขยับแค่บางส่วนของการเคลื่อนมือ (`minGain`)
- มือเร็ว: ตาม 1:1 และดูดกลับมาตรงตำแหน่งมืออย่างเร็ว
- นอกนั้น: ดูดกลับช้า ๆ ระยะห่างจึงไม่สะสม

| gain / ช่วงความเร็ว (px/s) / ดูดกลับเร็ว–ช้า | shake           | steady         | off     | edge     | delay          |
| -------------------------------------------- | --------------- | -------------- | ------- | -------- | -------------- |
| (ไม่มี)                                      | 1.84 / 1.76     | 13.6 / 22.0    | 18 / 17 | 100%     | —              |
| 0.3 / 60–400 / 150–2000                      | 1.63 / 1.23     | 10.2 / 17.0    | 26 / 26 | 100%     |                |
| 0.3 / 100–600 / 150–2000                     | 1.27 / 0.93     | 8.9 / 19.8     | 33 / 30 | 100%     |                |
| 0.3 / 150–800 / 100–2000                     | 1.00 / 0.76     | 8.7 / 14.0     | 39 / 34 | 100%     | 3 / 14 ms      |
| 0.25 / 150–800 / 100–2000                    | 0.97 / 0.70     | 8.4 / 13.4     | 41 / 35 | **90%**  |                |
| 0.3 / 150–1000 / 100–2000                    | 0.89 / 0.70     | 9.4 / 18.8     | 48 / 39 | **90%**  | 16 / −26 ms    |
| **0.3 / 150–800 / 60–2000**                  | **1.00 / 0.76** | **9.1 / 14.1** | 38 / 33 | **100%** | **−1 / 14 ms** |

(ตัวเลขซ้าย / ขวา = session 10-29 / 10-28)

gain ต่ำกว่า 0.3 หรือช่วงความเร็วกว้างกว่า 800 จะเริ่มเอื้อมไม่ถึงขอบจอ (edge 90%) ส่วนความหน่วงตอนกดอยู่ที่ 0–14 ms ซึ่งไม่รู้สึก

### รอบที่ 5 — E2E จับปัญหา: ลากช้า ๆ ปลายปากกาตามไม่ทัน ✗ → แก้

ใส่ใน engine แล้ว E2E บทพยากรณ์ล้ม: วาดได้ 11/12 เดือน

- ร่างกายสังเคราะห์วาดช้า ๆ ทีละเดือน (~120 px/s) จึงอยู่ในโซน "มือช้า" ตลอด
- **คำนวณ:** ลากช้าสม่ำเสมอที่ v จะตามหลัง (1 − gain) × v × τ_ช้า = 0.7 × 100 px/s × 2 s ≈ **140 px** ซึ่งน้องที่วาดช้า ๆ อย่างตั้งใจจะเจอแบบนี้จริง

ทางแก้ที่ลอง:

| ทาง                                             | ผล                                                                                                                   |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| แยก "ตั้งใจลาก" จากระยะสุทธิใน 400 ms           | ✗ การไหลตอนถือนิ่งไปทางเดียว 15–45 px ใน 400 ms เหมือนการลากช้า → steady กลับไปเป็น 12.0 / 20.2 เสียประโยชน์เกือบหมด |
| จำกัดระยะห่าง cursor–มือ (`maxGap`)             | cap 12 → 80 px: steady 12.0 → 9.1 · **cap 60 px: steady 9.4 / 14.1, shake 1.05 / 0.85** แทบไม่เสียประโยชน์           |
| ให้ฉากสลับเป็นโหมดตรงตอนวาด (`cursorPrecise()`) | บทพยากรณ์ปิด precision ช่วงวาด ปลายปากกาอยู่ตรงมือ 1:1                                                               |

ใช้ทั้งสองอย่าง: cap 60 px กันกรณีแย่สุดทุกที่ และโหมดตรงตอนวาด

### รอบที่ 6 — ผลกระทบกับท่าอื่น

- **ท่าปัด (research 019):** จับได้ 5/6 → **6/6** เพราะตอนมือเร็ว cursor ดูดกลับหามือเร็วจึงพุ่งแรงขึ้น ส่วนยืนเฉย / ชี้ช้า / ยกแขน ยังไม่ตบเองเลย (0) เท่าเดิม
- **คลิปวาด (ไม่มีโหมดตรง):** ความยาวเส้น 2,060 → 2,040 px ขอบเขต x 0–85% เท่าเดิม ท่าชี้กวาดยังถึงขอบครบ 0–100%
- **E2E ทั้งชุด 7/7 ผ่าน:** เล่นครบรอบ, จับโกงยิงได้ 14–18, วาดพยากรณ์ครบ 12 เดือน
- **mutation check:** ตั้ง `minGain = 1` (ปิดผล) แล้ว test ล้ม 3 ตัวตามคาด

## ทางเลือกที่ไม่เลือก

- **กรองจุดอ้างอิง (รอบที่ 1):** แย่ลงทุกค่า
- **กรองหนักขึ้น / deadband กว้างขึ้น (รอบที่ 3):** ไม่แตะการไหลความถี่ต่ำ และเพิ่มความหน่วง
- **แยกการลากด้วยระยะสุทธิ (รอบที่ 5):** การไหลจริงไปทางเดียว แยกไม่ออก
- **ดูด cursor เข้ากลางปุ่ม (target gravity):** ทำให้ความยากของปุ่มเปลี่ยน และไม่ช่วยตอนวางแม่เหล็กหรือตอนวาด (015 ทำแบบภาพอย่างเดียวไว้แล้ว)

## ข้อจำกัด / ต้องทดสอบต่อ

- **ลองสด:** รู้สึกนิ่งขึ้นจริงไหม และมี "หนืด" ตอนเลื่อนช้าไหม ถ้าหนืด ให้เพิ่ม `minGain` (0.3 → 0.4: steady 9.2 / 15.2)
- ข้อมูลมาจากผู้ใหญ่คนเดียวบนจอโน้ตบุ๊ก เด็กอาจโยกแขนมากกว่านี้
- ความเร็วเป็นสัดส่วนของจอ (`aspect` 16:9) ถ้าทีวีหน้างานไม่ใช่ 16:9 ต้องแก้ค่า
